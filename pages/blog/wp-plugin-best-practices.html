Coding Standards

Best Practices for Enterprise WP Plugin Development

Strict coding standards, database query hygiene, capability barriers, and cryptographic verification for professional WordPress engineering.

JH
Jewel Hossain WordPress & Systems Engineer
Apr 08, 2024 · 8 min read · Verified Technical Guide

Writing WordPress plugins that survive version upgrades, pass WordPress.org repository reviews, and meet enterprise security standards requires adherence to proven architectural patterns. Here are the core standards enforced on every production project.

1. Strict PHP Type Declarations & PHPStan Analysis

WordPress core is historically untyped. However, modern plugin development should mandate declare(strict_types=1); on every PHP file and run PHPStan Level 8 static analysis in CI/CD pipelines to eliminate type errors before code ever reaches production.

phpstan.neon NEON 
parameters:
    level: 8
    paths:
        - src
    scanFiles:
        - vendor/php-stubs/wordpress-stubs/wordpress-stubs.php
    checkMissingIterableValueType: true
    checkGenericClassInNonGenericObjectType: false

2. Nonce Verification & Capability Checks

A secure plugin never trusts incoming request headers. Every privileged action requires two independent validation checks:

  • Intent (Nonce): Verifies that the request was explicitly initiated by the user from an authorized form.
  • Permission (RBAC): Verifies that the authenticated user possesses the required capability (e.g. edit_posts or manage_options).
src/Security/RequestGuard.php PHP 8.3 
declare(strict_types=1);

namespace Jewel\BestPractices\Security;

final class RequestGuard
{
    public static function authorize(string $action, string $nonceField = '_wpnonce'): void
    {
        if (!current_user_can('manage_options')) {
            wp_die(esc_html__('Unauthorized access.', 'text-domain'), 403);
        }

        if (!isset($_REQUEST[$nonceField]) || !wp_verify_nonce((string)$_REQUEST[$nonceField], $action)) {
            wp_die(esc_html__('Security token expired. Please refresh.', 'text-domain'), 403);
        }
    }
}
Security Audit Note: Failure to check capabilities alongside nonces is the #1 vulnerability identified in third-party WordPress plugin security audits.

3. Clean Uninstall Lifecycle: Respecting the User's Database

A well-behaved plugin must clean up after itself. Never leave orphaned options, transients, or custom tables behind when a user permanently deletes your plugin. Provide a dedicated uninstall.php file rather than relying on deactivation hooks.
